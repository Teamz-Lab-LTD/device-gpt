# DeviceGPT D1 retention — measurement, 2026-09-25

**Outcome: no code changed.** The cohort that carries the retention fixes is one day old
(25 users with a complete D1 window). Per STEP 1's own rule, that is too small to judge.
Changing anything now would also make vc48's effect unmeasurable.

## Live version

Play production: **3.1.29 (vc48)**, `status=completed`, **100% rollout** (full, not staged).
Read from `edits().tracks().get` in a fresh edit — not from an upload script's own claim,
which reported "live" on vc46 while the API still said `draft`.

## D1 / D3 / D7 by cohort

Cohorts are `firstSessionDate` single-day cohorts (DAILY granularity rejects multi-day
cohorts), summed. Window 2026-08-11 .. 2026-09-23 so every D1 window is complete.

| cohort | users (day 0) | D1 | D3 | D7 |
|---|---|---|---|---|
| pre-vc43 (≤3.1.23) | 130 | **6.9%** (9) | 1.5% (2) | 0.0% (0) |
| vc43-45 (3.1.24-26) | 56 | **5.4%** (3) | 1.8% (1) | 0.0% (0) |
| vc46+ (3.1.27-29) | **25** | not measurable | — | — |
| all installs, no version filter | 183 | **6.6%** (12) | 1.6% (3) | **0.0%** (0) |

Three things this table does and does not say:

- **vc43 did not move D1.** 5.4% vs 6.9%. But 3 returners out of 56 has a 95% interval of
  roughly 1%–15%; it overlaps pre-vc43 completely. The correct reading is *no detectable
  difference*, not *a regression*.
- **D7 is 0 across 183 users.** Not "low" — zero. Nobody was present on day 7.
- **vc46+ cannot be read.** 25 users with a complete D1 window, all installed 2026-09-24.

I checked one hypothesis and it was wrong: I expected the `appVersion` filter to suppress D1,
because a user who updates overnight returns carrying the *new* version and would be filtered
out of their install cohort. The unfiltered number (6.6%, n=183) matches the filtered ones, so
the filter is not distorting the result. Recording it because the reasoning looked sound.

## The denominator is inflated — every D1 figure here inherits it

GA4 `first_open` does not equal new installs. Over 2026-07-01 .. 2026-09-08, the window where
Play data also exists:

```
Play "Daily User Installs" : 119
Play "Install events"      : 141
GA4  first_open events     : 288      <- 2.42x Play user-installs
```

The excess concentrates on **release days**:

| date | Play user installs | GA4 first_open |
|---|---|---|
| 2026-07-10 | 3 | **39** |
| 2026-09-08 | 3 | 16 |
| 2026-09-24 | (no Play data yet) | **46** vs a 3/day median |

On 2026-09-24, `first_open` fired on 3.1.27, 3.1.28 and 3.1.29 — three builds released hours
apart — and on 3.1.26, which was already superseded.

**Mechanism not established.** There is no `resetAnalyticsData()`, no
`FirebaseInstallations` deletion and no manual `first_open` logging in `app/src/main/java`.
Candidates remaining: `first_open` firing on update, reinstalls by the same user (Play counts
a user once, GA4 counts each app instance), or one user across several devices. Only the
first explains the release-day concentration.

What follows regardless of mechanism: **the fleet verdict's 8% D1, and every number in the
table above, are computed against a denominator that is roughly 2.4x the real new-user count.**
Whether that biases D1 up or down depends on how the extra instances behave, which is not known.
Fixing this is a prerequisite for trusting any retention target, including the 10% floor.

## Where users are lost

Users fired each event, as a share of that cohort's `first_open` users:

| event | pre-vc43 | vc43-45 | vc46+ |
|---|---|---|---|
| `first_scan_completed` | 85.6% | **88.7%** | 42.9%* |
| `premium_paywall_shown` | 77.6% | 64.5% | 33.3%* |
| `premium_purchase_completed` | 0.8% (1 user) | 0% | 0% |
| `review_requested` | **110.4%** | 90.3% | 7.1% |
| `baseline_snapshot_written` | **0** | **0** | **10 users** |

\* vc46+ installed 2026-09-24; these are one-day partials, not a drop.

**There is no broken step inside the app.** 86–89% of users complete the first scan. The
funnel does not leak — it ends. Everything is lost between "saw the score" and "opened it
again the next day", which is not a step that can be fixed, because it is the absence of a
reason to return.

Two things are worth naming for the next pass:

1. **The paywall is the loudest thing after the scan.** 97 users saw `premium_paywall_shown`
   **703 times** — 7.2 per user — for **one purchase, ever**. vc43-45 shows 4.6 per user. The
   only written 1-star review in the export says *"Não vi nada de inovador e cheio de Ads"*,
   and the same complaint appears in English five months earlier. This is the leading STEP 2
   hypothesis, but it is a hypothesis: nothing here proves the paywall causes the non-return.
2. **`review_requested` reached 110% of `first_open` users on pre-vc43** — more prompts than
   users — which is what the Remote Config note describes and what the 24h delay was meant to
   stop. On vc46+ it is 7.1%.

## The one thing already confirmed working

`baseline_snapshot_written` fired for **10 users on vc46+, and for 0 users on every earlier
version**. That is the Device Timeline defect fixed yesterday: `recordDailySnapshotIfDue()` was
the only writer of the row type `DeviceTimelineSection` renders, and its sole call site sat
inside `if (widgetV2)` — a flag that is false in production, while `timeline_enabled` is true.

The Timeline — the app's only "come back and see what changed" surface — had **never** had data
for any user until 2026-09-24. Every D1 number in this document was measured against a build
where it was empty. That is the strongest reason not to touch anything else yet.
